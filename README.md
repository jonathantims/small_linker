# small_linker

small_linker is a small, fast, simple linker. It links the code and does not add legacy bloat. It does not waste padding, and in certain cases it produces significantly smaller binaries than a general-purpose linker.

It converts one Microsoft I386 or AMD64 COFF object from ml.exe, ml64.exe, or cl.exe into a compact PE32 or PE32+ executable. The program is freestanding: it does not use the C runtime, and the executable imports only kernel32.dll. It is meant for freestanding programs that do not require the C runtime or COFF library archives.

**Important:** This project is also intended as an educational tool for my children. The source is there to be read and learned from, as well as to be used as a linker.

## Features

- Links one I386 or AMD64 COFF object into a PE32 or PE32+ executable.
- Supports 32-bit and 64-bit objects generated by MASM and Visual C.
- Merges subsection names such as `.text$*` and `.rdata$*` into their canonical PE sections.
- Supports common I386 DIR32, DIR32NB, REL32, SECTION, and SECREL relocations.
- Supports AMD64 ADDR64, ADDR32, ADDR32NB, REL32 through REL32_5, SECTION, and SECREL relocations.
- Generates named DLL import tables, IAT entries, and MASM-compatible jump thunks.
- Validates object structure, bounds, symbols, relocations, and arithmetic overflow before writing an executable.
- Optionally packs a small read-only `.rdata` section into unused PE header padding.

## Build

Visual Studio with the x64 C build tools is required. `config.bat` is the single place that points at the compiler. It sets `VCVARS64` to the full path of `vcvars64.bat` when that variable is not already set. Edit the default in `config.bat` for this machine, or set `VCVARS64` in the environment before building to override it for one run.

From this directory:

```bat
build.bat
```

The script loads the Visual Studio environment, then compiles `small_linker.c` and `tests\link_tests.c` as 64-bit C11 programs with warnings treated as errors. Both executables are linked without the C runtime. Outputs go in `out\`:

- `out\small_linker.exe`
- `out\link_tests.exe`

`out\` is omitted from source control.

## Usage

```text
small_linker input.obj [/out:program.exe] [/entry:symbol]
             [/subsystem:windows|console]
             [/import:dll,symbol[,symbol...]] [...]
             [/pack-headers]
```

Example:

```bat
small_linker program.obj /out:program.exe /entry:start ^
    /subsystem:console ^
    /import:kernel32.dll,ExitProcess,GetCurrentProcessId ^
    /import:kernel32.dll,GetTickCount,GetLastError
```

If `/out` is omitted, the output file is `a.exe`.

The default subsystem is Windows GUI. Use `/subsystem:console` for a console executable or `/subsystem:windows` to select the default explicitly.

If `/entry` is omitted, the linker first checks the object's `.drectve` section for an `/ENTRY:` directive, then searches for these defined symbols in order:

1. `mainCRTStartup`
2. `WinMainCRTStartup`
3. `wWinMainCRTStartup`
4. `_start`
5. `start`
6. `main`

All referenced external symbols must be declared with a repeatable `/import` option. Each option accepts one DLL followed by one or more comma-separated symbol names. Repeating `/import` for the same DLL adds more symbols to that DLL's import table. Invalid input and unsupported features produce a diagnostic and a nonzero exit code.

A bad object or a bad option prints `small_linker: error: ...` to standard error and exits with status 1.

`small_linker --self-test` checks the linker and writes `out\self_test.txt` next to the executable. Cases that must be rejected are run as separate linker processes, because a failure prints the diagnostic and exits.

## DLL imports

The linker supports named imports in two object-code forms.

### Direct function symbols

MASM can declare and call an imported function normally:

```asm
extrn ExitProcess:proc

mov ecx, 73
call ExitProcess
```

small_linker resolves the undefined function to a generated six-byte indirect jump thunk appropriate for the input architecture. The runtime path is:

```text
call -> thunk -> IAT -> DLL function
```

### Direct IAT symbols

Visual C emits direct IAT references when a function is declared with `__declspec(dllimport)`. MASM generators can use the same form:

```asm
extrn __imp_ExitProcess:qword

mov ecx, 73
call qword ptr [__imp_ExitProcess]
```

The `__imp_ExitProcess` symbol resolves directly to the generated Import Address Table slot, so no jump thunk is required. The runtime path is:

```text
call -> IAT -> DLL function
```

The `__imp_` form is recommended for generated MASM because it avoids an additional indirect branch and the six-byte thunk. Standard x86 C name decoration, including `__imp__Name@N` and `_Name@N`, is recognized automatically. Both forms use the same linker option:

```text
/import:kernel32.dll,ExitProcess,GetCurrentProcessId
```

Additional symbols from the same DLL can be declared in another option:

```text
/import:kernel32.dll,GetTickCount,GetLastError
```

Import by ordinal and `.lib` import-library parsing are not supported.

## Visual C-style calls from NASM

NASM can use the same direct Import Address Table symbols emitted by Visual C. This avoids the linker-generated direct-symbol jump thunk.

For 64-bit code, use NASM's win64 format, reserve the required Windows x64 shadow space, align the stack before the call, and call through the `__imp_<symbol>` pointer:

```nasm
default rel
bits 64

global start
extern __imp_ExitProcess

section .text
start:
    sub rsp, 40
    mov ecx, 73
    call [rel __imp_ExitProcess]
    int3
```

Build and link it with:

```bat
nasm -f win64 program.asm -o program.obj
small_linker program.obj /out:program.exe /entry:start ^
    /subsystem:console /import:kernel32.dll,ExitProcess
```

Windows x64 passes the first integer argument in ECX. The 40-byte stack adjustment provides 32 bytes of shadow space while maintaining 16-byte alignment at the call site. ExitProcess does not return; `int3` prevents accidental fall-through if it unexpectedly does.

For 32-bit stdcall code, use NASM's win32 format and the standard Visual C decorated IAT symbol:

```nasm
bits 32

global _start
extern __imp__ExitProcess@4

section .text
_start:
    push dword 73
    call [__imp__ExitProcess@4]
    int3
```

Build and link it with:

```bat
nasm -f win32 program.asm -o program.obj
small_linker program.obj /out:program.exe /entry:start ^
    /subsystem:console /import:kernel32.dll,ExitProcess
```

The `@4` suffix records the four bytes of stack arguments accepted by the stdcall function. small_linker automatically matches `__imp__Name@N` and `_Name@N` COFF symbols to the undecorated DLL export name supplied to `/import`.

## Freestanding C

C objects must provide their own entry point and avoid implicit CRT dependencies. Imported functions must use `__declspec(dllimport)`.

Typical compile commands are:

```bat
cl /c /O2 /GS- /Zl /Fo:program_x64.obj source.c
path\to\Hostx64\x86\cl /c /O2 /GS- /Zl /Fo:program_x86.obj source.c
```

The executable architecture is selected automatically from the COFF input. I386 objects produce PE32 executables and AMD64 objects produce PE32+ executables.

## Packed headers

The `/pack-headers` option stores a small read-only `.rdata` section in otherwise unused PE header padding and omits its section header. This can save one 512-byte file-alignment block.

The option fails if `.rdata` does not fit or uses SECTION or SECREL relocations. Because the Windows loader maps header bytes read-only, packed data must never be written. Test packed executables with every required Windows version and security tool before deployment.

## Limitations

- Only one normal I386 or AMD64 COFF object is accepted.
- COFF archives and BigObj files are not supported.
- The linker does not search libraries or link the C runtime.
- Cross-object COMDAT selection is not supported.
- Imports by ordinal are not supported.
- Debug information is not emitted.
- Metadata-only sections such as `.drectve`, `.debug*`, and `.llvm*` are not copied into the executable.

## Tests

`build.bat test` builds both programs, runs the self-test, then runs `out\link_tests.exe`. The integration program compiles `tests\cl_exit.c` and `tests\app_state_sim.c`, writes the other COFF inputs itself, links them, compares results with `link.exe`, checks imports and packed headers, and writes `out\BENCHMARK_REPORT.md`. The self-test log is `out\self_test.txt`.

Run the tests through `build.bat test` so `cl.exe` and `link.exe` are on `PATH`. The integration program also needs the Visual Studio Hostx64 x86 compiler and linker.

No object files are stored in the repository. `link_tests.c` emits the return, relocation, direct-import, and header-padding objects into `out\test` before it links them.
